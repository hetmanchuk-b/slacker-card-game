# Lobby persistence and match handoff — Stage 7

## Approved seams

Stage 7 implements retained chat and actual next-match transitions at the existing persistence/runtime seams. `PostgresLobby` stores immutable lobby ownership, retained chat and the current game pointer. Tests cross `PostgresLobby`, `GameRuntime` and `PostgresSession` against real PostgreSQL. They cover retention, canonical context, idempotence, transactional handoff and rollback races, not browser authentication or UI readiness controls.

Owner/author session IDs are trusted stable guest identifiers, not cookie tokens. Stage 8.5 provides the separate `PostgresGuestAccess` credential/membership gate, described in `guest-access.md`. Future transport must use it to authenticate each operation and bind current-game seats; this storage interface is not a network payload or authenticated endpoint. No ownership transfer or additional gameplay rule is introduced.

`PostgresLobby.create(pool, binding)` idempotently binds a lobby to its owner session/seat; a conflicting owner is rejected. `PostgresLobby.open(pool, lobbyId)` recovers that stored binding without in-memory ownership metadata. These methods are private server operations, not authorization for a caller who merely knows the lobby ID. `postChat(input, nowMs, runtime?)` records original author, verbatim text and server-derived game/branch/scope context. Runtime-bound messages enter that runtime's queue before any database lookup, so a later card action cannot overtake their scope capture. Runtime time overrides the standalone pre-game timestamp argument. Whitespace is preserved; NUL/unpaired Unicode are technical input errors, not gameplay penalties. Pre-match messages require an empty current-game pointer. Retries preserve the original context even after rollback; changed payloads cannot reuse IDs. `messages(afterSequence?, limit?)` returns a stable ordered page; `message(messageId)` retrieves the original immutable record for Stage 8.11's authenticated queued evidence resolver. The resolver validates original author, scope, game and inherited-prefix provenance; retained abandoned chat is not relabeled after rollback. Chat is separate from rollbackable card history and survives forks and match changes.

## Authenticated retained chat — Stage 8.13

The operator approved an additive `postChat(input, nowMs, runtime?, options?)` admission hook. `ChatAdmissionOptions.admit` is trusted, bounded and non-reentrant; it runs inside the existing runtime observation (or serialized standalone host operation) before **any duplicate lookup or insertion**. False throws fixed `ChatAdmissionError('unauthorized')`; callback failure is sanitized unavailable. Neither creates a row or faults gameplay. Once admitted, the independent chat transaction drains; transport suppresses responses after caller expiry/disconnect rather than undoing a committed message. Existing trusted callers without options retain behavior; no migration, message/frame format or runtime API changes.

`PostgresGameHost.postChat` selects the actual current writer/context inside host serialization, then calls storage directly—never nest postChat's runtime observation inside another observation. No-game posting uses the existing standalone pointer guard. `chatHistory` performs bounded SQL paging after queued membership admission, without acquiring or exposing game state. Both operations are for durable lobby members, including no-game, non-roster and finished members; human controller status is irrelevant. Chat permission never grants card/procedure/history visibility.

Approved identity policy: `(lobbyId, messageId)` is the durable operation identity. Exact author session/seat and text must match; context, sequence and timestamp stay original across forks, recovery and successor adoption. A different requestId may retry the same message; one requestId with another new messageId is a different operation. RequestId correlates chat-page replies only, not a durable ledger or shared gameplay namespace. Changed text/author reuse returns fixed unavailable without exposing the prior record.

Transport replies use existing `makeChatPage` redaction. Post returns one immutable message; history returns a count/serialized-byte-bounded ordered prefix. Resume from the last returned sequence; gaps in global sequences are normal. Never truncate text or skip a row. An individually oversized trusted row yields fixed unavailable, not an endless empty page. Final credential checks occur in the prepared outbound slot before synchronous projection/emission. Cancelled history is discarded without disconnecting healthy participants; committed post replies retain their original correlation/context across resync. No automatic chat push, reliable outbox, UI, start or lobby-admission endpoint is introduced.

## Match transitions

`startMatch(request, inputs, current?)` accepts a server-approved next roster/configuration. `expectedGameId` and `expectedHead` pin the prior result; both are null for the first match. The head is checked again in the runtime queue and storage transaction, so an old result cannot authorize a start after rollback/refinish. It prepares a private initial runtime, then commits its frame, the prior game's rollback closure, the lobby pointer and the start receipt atomically. The old runtime's queue serializes this handoff against rollback. Preparation is not exposed or acknowledged before the transaction commits. `GameRuntime.handoff` does not run the ordinary old-game commit afterward. The successor takes the connection/writer lease; the retired runtime stops accepting mutations. Preparation failures leave the existing live match usable and do not close its writer. Failed handoff transactions fault/discard drafts, leaving the last durable old game recoverable and rollbackable. A successor INSERT failure rolls back the old frame/head too. A committed handoff seals the old window even after a process restart; start retries return the original game rather than preparing another one.

Lobby start receipts retain canonical request IDs/configuration. A caller must retry the same server-resolved request, not regenerate identities before looking up an existing intent through `startReceipt(commandId)`. That receipt contains private server card configuration: use it internally after authentication and never send it to a browser. Stage 8 will adapt browser intents to this internal interface. All subsequent traffic must route through the lobby's current live match; do not keep sending commands/connection notifications to the retired runtime. The transport must check both game ID and branch ID. Readiness/house-rule editing, bot strategy and bot policy across matches remain their existing later stages; this storage API receives a server-approved roster/context rather than inventing those policies. For lobbies created through authenticated guest access, the final transition rechecks the stored clockwise membership roster under the lobby lock and aborts stale preparation if a join won first. Empty membership preserves legacy trusted start behavior; it does not permit authenticated adoption of legacy lobbies. A failed handoff transaction still requires recovery from durable state. Stage 11a must add the agreed minigame-completion gate to the start transition before that feature ships.
