# Branch history and rollback — Stage 7

## Interface and scope

Continue at the approved persistence and runtime seams (`docs/architecture.md`). Tests use the real engine, `MemoryHistory`, and `GameRuntime`; only time/randomness are controlled. These branch tests cover integrity, atomic rollback, trusted authorization and timer restoration, not socket authentication or public history redaction. Separate real PostgreSQL coverage now exercises the durable session described in `postgres.md`.

`History.read(branchId?)` reads the active or a retained branch. `rollbackPoint(commandId)` resolves a completed action on the active branch to its private pre-action state and the action's occurrence time. `fork(expectedHead, request)` atomically validates and creates an active child branch at that point, retaining the abandoned future. `branches()` and `audit()` expose detached server-only metadata. `closeRollback()` is the storage hook used by runtime `closeForNextMatch()`; the latter serializes closure with rollback and verifies the match is still finished. Branch versions count the inherited prefix plus new branch actions.

A fork is authorized against the original game's owner seat, using a server-authenticated actor binding. It requires explicit acknowledgment that rollback cannot undo human knowledge. The runtime serializes rollback with gameplay and timeout callbacks; transport authentication remains Stage 8. Technical rejections never trigger gameplay punishment.

The pre-action time is the selected action's timestamp, not the preceding action's timestamp: a ballot submitted four seconds after voting began has a pre-action timer with six seconds remaining. A recorded `clock-rebased` event captures remaining running time at that point and rebases it to the actual rollback time. Already-paused nested timers stay paused. Current socket/controller presence is not restored from the past; the runtime decides whether the restored state must remain suspended.

Rollback is a new administrative operation, not a replay of old randomness. It restores the inherited game state and repetition ledger, including wins/results and pending procedures; it does not count abandoned future occurrences. A successful fork has a persistent-in-adapter audit record usable for an all-player notification. Do not expose the private point/snapshot to the owner UI. Stage 8.3 implements the metadata-only projection below; authenticated delivery and UI remain later work.

New branch commands must carry the new branch ID. Old callbacks are invalidated by the runtime generation and head guards. Connection notifications are live facts, not old gameplay commands. The original game creation may also be a target (empty pre-game state), without losing the stored owner binding or releasing the administrative command ID. A rollback targeting an earlier synthetic clock rebase uses that event's captured time, avoiding consumption of the abandoned timeline twice.

## Authoritative claim evidence — Stage 8.11

The approved `runtime.dispatchClaim` resolver receives detached active history and branch ancestry at a serialized committed point, with resolution/execution in the same job. `PostgresGameHost.submitClaim` supplies immutable lobby-scoped chat evidence. Action references resolve only from the active inherited timeline, using initiating actors and original scope (successful lead starts its new round; final action retains its old round). Chat uses stored author/scope/game and validates its original head against every nested ancestry cutoff. Inherited-prefix chat survives rollback; retained abandoned futures are not claim evidence. No arbitrary staging reads, client scopes, archive disclosure or new history/persistence contract is introduced. Exact accepted retries settle before re-resolution. Stage 8.12 binds owner-history selectors and rollback transport below; see `transport.md`.

## Owner-history projection — Stage 8.3

`src/projections/history.ts` provides `projectOwnerHistory(capture, viewer)` under approved D003. It accepts a narrow trusted committed capture compatible with `MemoryHistory.snapshot().value`, retaining the original owner and irreversible closure independently of rollbackable state. A bound non-owner or public viewer is denied with a fixed error; an uncreated game with no original owner has no game-history authorization. The projector never reads snapshots/card catalogs or calls live/action observation APIs.

Active and abandoned timelines contain one row per completed action: labels/recorded actors, violations, safe claim metadata and final decisions only. No faces, card handles, raw identifiers/events, ballot choices, selections, state previews or replayed reveals/peeks/transfers appear, even for the owner's own cards or previously public cards. The owner's current seat view remains separate. Unknown extra properties are not copied.

Display references use persisted branch ordinals and action versions; inherited rows identify their origin through ancestry. Audit links are projected without raw administrative command IDs, including pre-creation forks with no action. Only active/open rows expose rollback selectors. Stage 8.12 resolves these selectors against a fresh committed capture before constructing the existing trusted rollback command; it must still enforce warning acknowledgment and owner/head/closure checks. Archived rows are read-only, and closure suppresses all targets without deleting timelines or requiring a head-version change.

**Commit boundary:** `MemoryHistory` is a private staging interface. `snapshot().value` alone does not prove commitment, nor does matching `GameRuntime.read().head` prove a closure committed. Stage 8.6's server-private `runtime.subscribe` callback supplies a known committed serialized point: capture/project extra concrete history synchronously there before any await, or retain a validated committed frame. The generic History interface is unchanged; a later asynchronous draft read still proves nothing. Stage 8.12's `PostgresGameHost.observeHistory` also captures concrete history inside the existing read-only runtime queue, after checking published runtime health. No mutation can overtake that observation, so same-head closure and failed-draft boundaries are preserved. This does not replace storage recovery validation.

## Authenticated current-match administration — Stage 8.12

Transport authenticates immutable lobby ownership and current-game routing separately from live gameplay participation. Original owners retain metadata access after finishing or rollback to null state. Prepared history delivery reauthorizes and projects a fresh committed capture inside the wire slot; receipt-time epochs/generations fence resync/rollback/recovery. No hidden card IDs/faces, previews, raw commands/events or ballot selections are delivered.

The host resolves display ordinal/action selectors in `observe`, then dispatches outside the observer with exact canonical expected head/target/request/warning/actor and a fresh admission guard. A timer or action in between rejects optimistically. Retained branches permit accepted retry reconstruction without granting new rollback authority to archived rows; current head/owner/warning/closure/control checks still apply. No persistent request ledger or runtime API change is added.

Fresh committed rollbacks supply a public metadata-only actor/ordinal-target/result notice to authorized current participants, including pre-creation rollback with no action pair. This approved protocol addition never broadcasts owner history or private audit records. Duplicate/recovery/resync baselines do not replay it; delivery is bounded best-effort. Only the current lobby match is routable—historical-game access after successor start remains outside this increment. See `protocol.md` and `transport.md`.

## Approved bounded history pagination prerequisite

`owner-history-page` is an additive current-match owner reader; the original whole-history and ordinal rollback APIs remain unchanged. The pager first projects the complete allowlisted metadata view, then emits ordered branch descriptors, complete branch action rows and rollback audit entries in byte-bounded pages. This preserves inherited origins and cross-page claim references without exposing snapshots, faces, handles or other ballots. Selectors are identical to the original projector and remain subject to fresh rollback authorization/head/closure checks.

A stateless continuation binds offset to a SHA-256 digest of the complete public view, including same-head closure and audit. Each page obtains a new committed capture and reauthorizes the owner in the existing wire slot. Changed public history yields explicit stale status, requiring restart; cursor knowledge grants no access. Stable recovery may retain a snapshot identity. No stored snapshot/session ledger or persistence format is added. Full projection remains O(total history) per page; this bounds wire bytes, not history CPU/memory.

Representative trusted legal 2/4/8-seat match fixtures measured complete envelopes plus outbound allowance at 24,062/28,608/58,625 bytes. A retained final-action fork measured 39,956/47,425/97,174 bytes. The eight-seat retained timeline exceeds the 65,536-byte legacy bound, motivating explicit operator approval for this prerequisite. These measurements are trusted engine/runtime evidence, not browser acceptance. No timeline UI or rollback control is implemented by this prerequisite; see `protocol.md` for the exact new contract.

## Browser metadata timeline — Stage 9.13

The browser uses only `owner-history-page` through the existing shared connection. `OwnerHistory` strictly checks/detaches the public summary/branch/action/audit schemas, requires ordered progress under an identical snapshot/head/closure, and follows explicit cursors without assuming a short page is complete. No partial traversal can authorize selection. Metadata deliveries participate in epoch/sequence ordering but never install historical heads or faces as current state.

`OwnerHistoryView` renders named active/abandoned branches, inherited origins, action summaries and audit-only numbered rollback records in a keyboard-scrollable semantic table. Only complete active/open rows with server-supplied selectors expose native radio selection. Selection is local presentation, bound to that history snapshot; refresh, stale/malformed pages, authoritative live changes and connection/route/epoch/rollback resets invalidate it. No previews, hidden IDs/cards, other ballots, warning confirmation or rollback dispatch are implemented. Finished/null-state owner metadata access does not require active-player status; the server remains the authority.

Three browser cases distinguish real authorization and authenticated Node null/abandoned setup from explicitly engine/projector-fixtured finished and large-history rendering. No full UI-completed match or browser rollback is claimed. Large-history fixture measurements and verification limits are recorded in `IMPLEMENTATION_PLAN.md` and `docs/browser-client.md`.

## Durable runtime seam (Stage 7)

Extend the approved persistence/runtime seams with an awaited runtime `commit(checkpoint)` adapter. A complete queue job (including logical suspension, receipts and live control changes) is staged in private history; one database transaction stores its versioned history archive, active-state snapshot, checkpoint and revision. The public runtime view and acknowledgment are published only after commit. Commit failure faults the runtime; discard its draft and recover from storage. Do not schedule gameplay callbacks before the initial durable commit.

`PostgresSession.open(pool, gameId, rootBranchId)` owns one advisory-locked connection per game. It provides the loaded `history`, last `checkpoint`, awaited `commit(checkpoint)` and `close()`. A second writer must be refused. SQL migrations run explicitly through `migrate(pool)`, not silently during game creation. Recovery replays a versioned operation archive, including forks/closure, and checks it against the stored snapshot. Tests cross these public interfaces against real PostgreSQL and `GameRuntime`, not SQL-call mocks. Fault injection is restricted to the test database. Socket authorization remains outside this seam; the pure metadata-only owner-history projection is described above.

## Snapshot-assisted recovery seam

`MemoryHistory.snapshot()` captures a versioned, integrity-checked materialized cache of all branch states and indexes at an operation-archive offset. `restoreSnapshot(archive, cache)` validates the cache and its binding to that archive prefix, restores the prefix without executing its gameplay events, then replays only the operation tail. Full `restore(archive)` remains an independent replay path. Tests compare both paths through existing history/runtime interfaces, including rollback metadata and nested timers; snapshots remain private storage data, never accepted from browsers.

## Durable implementation and remaining work

`MemoryHistory.archive()` records a versioned, replayable operation archive, including forks and irreversible closure. `MemoryHistory.restore()` replays it without fresh randomness and restores ancestry, ownership and deduplication metadata. JSON object key ordering is not command identity: action duplicate checks use structural equality, including after JSONB round-tripping.

`PostgresSession` now persists that archive, the active-state snapshot and runtime checkpoint in one awaited transaction. The in-memory `History` remains a private staging interface; its synchronous append alone is not a durable acknowledgment. `GameRuntime.read()` exposes a detached committed view, never an in-flight storage draft. Failed commits make the runtime unusable until recovered; do not reuse its staged history.

Snapshot-assisted recovery is implemented and verified against full replay, including a snapshot followed by further fork/closure operations. PostgreSQL defaults to that cache path while retaining explicit full replay for audits and fallback for old cacheless frames. Durable lobby chat and actual lobby transitions are now implemented through `PostgresLobby`; start uses queued runtime handoff and one transaction, not the legacy preflight guard. Closure/branch metadata and start receipts survive recovery. Storage compaction/profiling remain release-hardening work. Minigame lifecycle is a later Stage 11a integration. See `postgres.md` for setup, tests and current operational limits.
