# Durable local game host — Stage 8.7

`src/server/game-host.ts` implements `PostgresGameHost`, a server-private, single-process registry over the existing PostgreSQL leases, runtime and lobby transition APIs. It is not a running server, an authentication boundary, a projection or a network delivery service. No schema, engine rule, runtime/checkpoint contract or dependency changes are required.

## Interface

Construct with a configured `pg` pool. Default inputs use `systemInputs`; tests inject clock/randomness/command IDs through the optional `inputs(onError)` factory. The host wraps scheduled tasks to check runtime health after settlement: runtime deadline failures are consumed internally and cannot be detected solely through a clock rejection reporter.

- `subscribe(lobbyId, receive, report?, expectedGameId?)` registers a server-private lifecycle observer. Each live writer supplies an action-free initial `HostPublication` and subsequent exact runtime publications under its epoch. Release first sends `invalidated` synchronously; successfully installed recovered/successor writers rebind a new baseline. The optional expected game pins initial registration only. Returned unsubscribe is immediate/idempotent. Callback/reporter throws/rejections cannot fault storage or block the host; their promises are not awaited. Registration may acquire/restore an existing writer, unlike the runtime's purely read-only subscription. No callback is installed during private successor preparation.
- `read(lobbyId)` resolves the durable current-match pointer and returns `null` or a private `{ epoch, snapshot }`. Unknown/unavailable lobbies fail rather than creating a lobby/game.
- `withCurrent(lobbyId, expectedGameId, operation)` checks current routing and runs a trusted server operation against its live runtime and epoch. A stale game is rejected, never silently routed to its successor. Ordinary-play versions/turns are not gated here; use existing runtime branch/controller checks. Callers must not retain writable runtime references or bypass host ownership.
- `submitClaim(lobbyId, expectedGameId, boundRequest, dispatchOptions?)` uses the existing writer and `runtime.dispatchClaim`; chat lookup and authoritative scope/actor/provenance resolution run inside that runtime job. It returns only the ordinary private runtime result, never raw evidence. The caller supplies fresh authorization through the admission guard. No schema or receipt format changes are introduced.
- `observeHistory(lobbyId, expectedGameId, operation)` supplies a detached narrow `OwnerHistoryInput` and writer epoch inside `runtime.observe`. Concrete history is captured only after `runtime.read()` verifies health at that committed queued point, including same-head closure. Callback must be bounded/non-reentrant; never await network delivery. Input remains raw private server data requiring projection/authorization.
- `rollback(lobbyId, expectedGameId, boundRequest, dispatchOptions?)` resolves ordinal selectors in a committed observation, checking immutable owner, then exits observation before dispatch. Retained branches reconstruct canonical accepted retries; new requests still face runtime exact-head/warning/closure/control checks. Intervening actions reject optimistically, never retarget. No runtime or persistence format/API changes are needed.
- `postChat(lobbyId, boundChatInput, nowMs, admissionOptions?)` selects the actual current writer under host serialization, then lets `PostgresLobby.postChat` capture context/time and perform admission inside its single runtime observation. Standalone storage is used only with no current game. Independent chat SQL errors do not fault a healthy runtime. Message IDs retain original immutable identity/context; no new retry ledger.
- `chatHistory(lobbyId, afterSequence, limit, admissionOptions?)` performs queued lobby-membership admission before reading retained SQL rows without acquiring a game writer or projecting state. Results are raw private server data; caller must redact/bound and reauthorize delivery. Both chat methods permit lobby members outside the current match and do not grant game visibility.
- `attach(freshMembership, signal?)` records one authenticated connection and returns an idempotent async detach handle. The additive optional AbortSignal is checked inside queued admission, before connection insertion/presence, so cancelled transport work cannot publish a transient reconnect; already-admitted atomic commits still drain before detach. The membership must come from a fresh guest-access check, never client-supplied fields. A stale `currentGameId` rejects attachment. Multiple connections for one seat produce only aggregate presence transitions. Lobby-only members are tracked for future matches but cannot enter an existing match's roster.
- `recover(lobbyId)` disposes the old runtime, releases its session, restores durable state and reconciles the surviving live connection ledger. It does **not** checkpoint a possibly failed draft or rerun any command. Retry the original command ID separately to consult durable receipts.
- `startFromIntent(lobbyId, { id, actorSessionId, expectedHead }, admit)` is the approved Stage 8.14 authenticated orchestration seam. Its bounded non-reentrant callback returns fresh owner membership or null; exceptions become sanitized unavailable. Inside host serialization, authorize before receipt lookup, compare original actor/expected head on a retry, and return its stored game without restoring a writer or preparing new IDs/roster. A new request validates current pointer/exact finished head (or genuine no-game), owner-first 2–8 roster, then generates opaque game/branch/card IDs. Admission repeats in storage and inside queued handoff before closure. Known denial returns false to downstream gates, preserving unauthorized versus infrastructure unavailable. Final SQL roster recheck rejects intervening joins without regenerating canonical configuration.
- `startMatch(lobbyId, trustedCanonicalRequest)` delegates to `PostgresLobby.startMatch` and adopts only the successfully committed live successor. Returned start results omit runtime/session references. Existing atomic owner/head/roster/receipt checks remain authoritative. Existing trusted callers retain behavior; browser intents now use startFromIntent. Stage 8.18 adds a final transactional agreement-acceptance gate to member-backed new starts through both entry points, not a general willingness-to-play flag. Accepted canonical retries resolve before that gate/reset; legacy zero-member lobbies remain compatible. Late acceptance/roster refusal preserves the original writer and rollback window through deferred closure. The host does not change routing or serialize new workflow HTTP mutations; guest access owns their credential/lobby/game-head transactions. Future minigame gating remains deferred.
- `close()` rejects new work, drains already queued operations, checkpoints healthy entries, disposes every runtime and closes every leased session, even if one checkpoint fails. The returned promise is stable, including its failure. The caller closes the pool afterward. Detach after shutdown is harmless.

## Ownership, faults and presence

Lifecycle operations and trusted callbacks share a local serialized queue. Concurrent cold requests restore a game once and reuse the same writer/epoch. Keep callbacks bounded and **never re-enter the host from an awaited callback**. Independent runtime deadlines retain their existing per-game queue. This deliberately small registry can head-of-line block unrelated lobby operations; parallel lifecycle queues, idle eviction and distributed execution are not implemented.

Acquisition looks up an existing durable root branch with a committed revision before opening its lease. It always restores the stored checkpoint, never fabricates a missing game or starts a fresh runtime over recovered receipts. Failed restoration or presence reconciliation disposes/closes its resources. Writer contention returns fixed `game-unavailable`; no automatic retry, lock stealing or integrity-error retry is introduced. A later request can retry acquisition. PostgreSQL may release a destroyed backend's lease slightly after local close completion.

Dispatch callback faults and settled deadline failures evict faulted entries. A callback that swallowed a dispatch error is detected on the next acquisition. Epoch checks prevent old clock cleanup from evicting a replacement. A failed detach lookup also evicts cached lobby entries, preserving the real departure in the ledger rather than allowing stale connected gameplay. Recovery starts with old sockets disconnected, then reconnects only seats with surviving host connections; timer/receipt/controller recovery uses the existing runtime contract.

A fresh random epoch identifies each live writer lifetime. Stage 8.10's approved `HostPublication` is either `{ type: 'publication', epoch, publication, rollback? }` or `{ type: 'invalidated', epoch }`. Observer lifetimes follow the lobby across host-owned recovery/actual handoff, but never expose a prepared successor. Invalidation precedes awaited disposal/session release; old subscription callbacks cannot forward after it. Recovery/successor installation supplies baseline only, not inherited/recovered actions. Stage 8.12 adds optional `rollback` metadata, allowlisted synchronously from the committed fork's capture, including a null-state rollback with no action pair. Only fresh rollback publications carry it; initial/recovery baselines never replay it. The host does not allocate transport sequences, retry delivery, cancel already-running consumer promises or project raw publications. Stage 8.10's `PenkyTransport` handles generations, authorized projections and bounded acknowledged delivery; see `transport.md`.

## Authorization and remaining integration

All input bindings, callbacks, snapshots and runtime publications are trusted **private server data**. Reauthenticate membership/owner privileges on each external operation and separately verify current-match participation for live/gameplay payloads. This registry does not itself close expired/revoked sockets, enforce origin/rate/byte limits, implement HTTP/Socket.IO or authorize browser/bot payloads. Stage 8.8's separate `PenkyTransport` integrates authenticated attachment/private resync and initial limits/watchers; see `transport.md`. Stage 8.9 uses `withCurrent` plus the approved optional runtime admission guard for a bounded gameplay subset and durable acknowledgments. Stage 8.10 adds bounded best-effort live/action delivery through this lifecycle seam. Stage 8.11 adds queued authoritative claim resolution through `submitClaim`; the transport binds all three existing evidence variants. Stage 8.12 integrates current-match owner-history capture, ordinal rollback routing and allowlisted notices. Stage 8.13 adds bounded retained-chat routing, with approved messageId identity/requestId correlation and queued membership admission. Stage 8.14 adds canonical authenticated start retries through the same non-enqueuing private adoption helper. Denied admission preserves a healthy old writer; failed atomic transitions and post-commit reconciliation retain existing eviction/recovery policy. Canonical lobby-creation orchestration and any reliable-delivery/outbox feature remain later work. Do not use lobby membership as a permanent authorization capability.

Real disposable PostgreSQL coverage in `src/server/game-host.postgres.test.ts` includes cold/concurrent acquisition, competing leases, connection aggregation, stale routing/bindings, receipt/baseline recovery, dispatch/deadline faults, failed detach lookup, corruption, post-restore presence failure, multi-game shutdown failure, nested timer recovery and failed/successful successor adoption. These are library/database tests, not isolated online-client or browser verification.
