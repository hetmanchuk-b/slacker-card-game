# Architecture decisions — initial implementation

## Agreed implementation seams

The implementation plan and approved architecture establish the test seams:

- **Engine:** command decision, event application/replay, and invariant validation. This catches rules and deterministic transitions, not socket authentication or visual behavior.
- **Runtime:** serialized commands, clock, and randomness. This catches delivery ordering and timer suspension, not rendering.
- **Projections:** authorized player/history views. This catches information leakage, not whether a human remembers a revealed card.
- **Persistence:** atomic append and branch recovery. This catches lost/duplicated history, not transport delivery.

Tests cross these interfaces. No tests against private helper call order are required.

## Determinism and identity

- Use branded string IDs to prevent accidental mixing of seats, cards, actions, and branches.
- Card IDs are independent of faces. Production IDs come from cryptographically generated opaque identifiers.
- The engine receives time and bounded random integers as inputs, rather than importing system time or crypto.
- Creation records the card catalog, shuffled deck, and first recipient in its event. Replaying it does not re-run randomness.
- One accepted command produces one atomic action containing one or more events. It is a valid history unit; internal events are not independent rollback targets.
- A rejected command produces no action. A recognized in-game violation produces an accepted action with a violation outcome.
- Engine state and raw events are private authoritative data. They must never be sent directly to browsers or bots.

## Baseline current-state projections — Stage 8.1

`src/projections/game.ts` provides `projectGame({ head, state }, viewer)`, a pure allowlisted view of a committed server snapshot. The viewer is a trusted server binding (`seat` with seat ID, or `public`), not a browser credential. Unknown seated viewers and game/head mismatches fail with fixed errors that do not echo identifiers or state. No engine, runtime or persistence contract changes are required.

| Viewer | Private current data | Shared current data |
| --- | --- | --- |
| Bound active seat | Own hand faces and opaque own-stump command handles, never closed stump faces | Clockwise seat IDs/status/counts, public table bottom-to-top, deck/discard counts, safe phase/result fields and head |
| Bound finished seat | Same seat-local rights, no additional access after exit | Same shared fields |
| Public viewer | None | Same shared fields |

Ownership does not elevate this view. Output objects/arrays are newly constructed; extra properties on private inputs are not copied. Only own-hand and public-table IDs are resolved to faces. The host remains responsible for face-independent opaque IDs and for supplying committed rather than staged snapshots.

Dealing/reveal/pre-game-penalty phases expose only their type. Between-round and round phases expose leader/turn, round number and fixed target as applicable; no dealing-turn hint, trump, reveal face/timer or permanent trump record is included. Current results retain the existing revision 1.3 contracts; revision 1.4 changes remain Stage 11a work.

This baseline remains deliberately minimal. Stage 8.2 adds separate scoped live/action projectors below, preserving `projectGame`'s contract. Neither projector is a bot memory API or a network endpoint; metadata-only owner history is a separate Stage 8.3 projector below, and authenticated resync is integrated separately in Stage 8.8 below.

## Scoped live and action projections — Stage 8.2

`projectLiveGame(snapshot, viewer, nowMs)` composes the baseline with current procedure/control views and authorized transient disclosures. Time is supplied by the trusted server, never read from a system clock in projections. D002 records the approved presentation policies:

- Reissue the private initial-recipient notice only at dealing `drawCount=0` to the selected seat. Out-of-turn draws do not consume it.
- Show the final card only while its reveal timer runs with positive remaining time. Hide it during claims/disconnect suspension and at the deadline even if the expiry callback is delayed. Resume with the captured remainder, never a new ten seconds. Normal own-hand visibility is unaffected.
- Never expose `peekedStumps` in a current/reconnect view.

Claim/withdrawal views select safe claim fields, eligible seats, timer durations and only the viewer's own ballot/approval. The suspended ballot is projected explicitly. Penalties expose recipient/reason and only the donor's own reserved selection; recipients do not learn reserved cards before completion. Presence selects seat/connected/controller fields. Replacement timers continue independently during gameplay suspension; no raw control audit, receipts or timestamps are returned.

`projectAction({ before, after, action, delivery }, viewer)` is a **fresh committed action response**, not history or a reconnect feed. It checks same-game/same-branch adjacent heads and deterministic replay equality, replacing replay diagnostics with a fixed error. Only allowlisted movement/violation observations are returned, as one complete list: played cards and automatic pickups remain observable even when the final table is empty; draws/opens hide faces from other seats; the last draw does not create a permanent public reveal record. Illegal peeks are sent only to the actor for `delivery='fresh'`; duplicate deliveries yield no observations.

Nonzero penalty transfers consume the pre-action penalty's reserved choices plus any final response in the batch; faces go only to donor and recipient on the matching completion event. Newly auto-started penalties cannot receive a second user response within that same action; zero-card completion discloses no cards. No partial authoritative state is published.

**Caller obligations:** authenticate the viewer, use committed rather than staged snapshots, supply exact per-action pre/post pairs, and classify retries as duplicate. Replay consistency and a delivery tag do not establish freshness or durability; a stateless projector cannot prevent a trusted caller replaying identical fresh input. A runtime queue job may append several actions, so its overall head/state is not an individual action pair. The later committed-update publisher must integrate these APIs without leaking intermediate state or rebuilding private observations from history. Bot observation memory, rollback observation treatment and authorized delivery ordering remain their separate planned work.

## Metadata-only owner history — Stage 8.3

`projectOwnerHistory(capture, viewer)` implements D003 separately from current seat views. Its narrow trusted input is structurally compatible with `MemoryHistory.snapshot().value`: active/retained action histories, ancestry, immutable original owner, rollback closure and administrative audit. It does not read state snapshots or replay actions. Storage recovery/integrity validation and **successful commit capture** are caller obligations; taking a snapshot of an in-flight private draft does not make it committed. The pure projector checks viewer ownership before building output, validates structural game/head/ancestry references, and returns fixed errors without private diagnostics. Original ownership remains authoritative even when rollback restores a null pre-creation state.

Each branch has an active/abandoned label and one row per completed atomic action, including inherited prefixes and synthetic rollback rebases. Rows select action labels and recorded actors, violations, safe claim fields and final verdict/withdrawal decisions. They do not infer an original command when the event batch lacks that information. Individual ballot/approval values, penalty choices, card faces/handles (even public cards), initial-recipient notices, raw events, timestamps inside timer/rebase payloads and state previews are omitted. User-authored claim reasons remain text; the projector never enriches them with card data.

Branch numbers follow persisted ancestry insertion order. Display heads use `{ gameId, branch, version }`; claim links use their submission action version, and rollback audit links use ordinals. Raw branch/command/event/claim/procedure IDs are not display payloads, since they can contain correlated private data. Rows identify their original branch/version through nested ancestry. Administrative audit remains available even for a fork before creation with no synthetic action.

Rollback targets exist only on the active timeline while rollback is open. They select `{ expected: displayHead, beforeActionVersion }`, where the version identifies the completed action to roll back **before**, never an internal event. Inherited active-prefix actions and synthetic rebase actions are valid targets; abandoned-only futures are not. Closure disables every target even though it does not advance the action head. The later authenticated adapter must compare the observed display head with a fresh committed capture, resolve its branch/action ordinals to the server's private head/command ID, and invoke the existing runtime owner/warning/version/closure checks. These selectors are not standalone rollback authorization or a new persistence format.

No runtime/storage interfaces or live projection contracts change. This does not implement the future history endpoint, pagination/rate limits, delivery ordering or owner UI.

## External protocol boundary — Stage 8.4

`src/protocol/contracts.ts` declares an explicit browser intent union, version-1 envelope types and technical field limits. It is not derived from internal commands, so new system capabilities do not automatically become browser capabilities. `decodeClientMessage` accepts untrusted deserialized plain data, checks exact own fields at each known schema level, constructs detached validated intents, and returns only fixed technical failures. There is no actor/owner/controller/system/configuration authority, trusted claim scope, turn check or ordinary-play expected-version gate in the decoder.

`messages.ts` constructs safe acknowledgments/chat/start envelopes by selecting fields and fixed codes. State/action/history envelopes invoke authorized projectors directly rather than accepting arbitrary prebuilt payloads. Stream epoch/sequence is supplied by the future publisher independently of game-head versions. Immutable chat author session IDs, private start receipts, DB sessions, runtime objects and error diagnostics are never generic payloads.

See `docs/protocol.md` for shapes, exact procedure/evidence/ordinal references, technical bounds and retry semantics. This library does not implement authentication, lobby admission/readiness, raw transport byte/rate limits, canonical start-intent orchestration, committed capture/publication or queued evidence/selector resolution. Test-only explicit server bindings demonstrate accepted rule-breaking attempts and receipts; they are not production handlers or online verification. Existing internal runtime/persistence/projection contracts are unchanged.

## Committed update seam — Stage 8.6

`GameRuntime.subscribe(receive, report?)` attaches only to a live runtime, receives an initial detached baseline, and returns an unsubscribe function. This avoids leaking private successor preparation through construction callbacks. Successful committed changes produce one final private snapshot plus exact fresh action pairs; rollback includes only its new child rebase/reconciliation. Same-head control changes, closure and actual handoff have publication sequences/kinds independent of game-head versions. No runtime options, checkpoint/history/frame schemas or existing projection contracts change.

Delivery promises are not awaited. Listener/reporter throws or rejections cannot enter command/deadline fault handling or undo committed receipts. Each listener receives its own clone after commit, published-read installation and deadline arming. Async completion order/backpressure, reliable delivery, transport epochs and authenticated projection remain host responsibilities; see `docs/runtime.md` for the complete interface and its synchronous capture constraints.

Never serialize a `RuntimePublication` to clients/bots. Use its detached snapshot/action pairs for authorized projections. Additional committed history must be captured synchronously at the callback point, never reread from a mutable draft after an await. No subscription is installed on private match preparation; successor attachment follows the successful atomic start result.

## Timer and pause model

Gameplay phase, claim/penalty procedure, and live connection suspension are separate concepts. A disconnected player does not erase the procedure being interrupted. `GameRuntime` turns injected clock deadlines into serialized system commands. The engine records logical clock suspension and the IDs of timers that were running; nested timers already paused by a claim/withdrawal remain paused.

Live socket/presence information is not part of rollbackable game state. Recompute disconnection suspension after a rollback. A replacement vote belongs to runtime pause management and runs while gameplay timers are frozen. Runtime checkpoints capture presence/controllers, accepted receipts and control audit records separately from engine history; old sockets are disconnected on recovery. See `docs/runtime.md`.

## Storage decision

Stage 7 now uses PostgreSQL with `pg` and explicit checksum-checked SQL migrations. No ORM is required. Versioned private frames store the operation archive (action batches, ancestry, ownership and rollback audit), active snapshot and runtime checkpoint, including accepted command receipts. An optimistic head update and frame insert commit together on one leased connection. `History` is the synchronous private staging interface; the runtime's awaited commit adapter is the durability seam. Public state/acknowledgment publication waits for it. Real PostgreSQL tests cover faults and separate-process recovery. Recovery can load a validated materialized history cache and replay its operation tail; independent full replay remains available for auditing. Lobby chat is separately retained with original author/scope/head metadata. Actual next-match handoff atomically closes old rollback and commits the successor, lobby pointer and start receipt. See `docs/postgres.md` and `docs/lobby-persistence.md`.

## Guest sessions and ownership

- No account system is required for the first version.
- A server-issued opaque session token authenticates a guest. In browser deployment use a Secure, HttpOnly, SameSite cookie over TLS; validate origin on socket handshakes.
- Bind session identity to lobby membership and seat identity on the server. Never trust an actor/owner ID supplied by a browser payload.
- Reconnecting uses the same session; a display name or a lobby code is not a reconnect credential.
- Persist the lobby owner's session binding. Owner privileges are checked on every administrative command.
- No implicit host transfer or spectator access to private history is introduced by this decision. Obtain agreement before adding host-transfer behavior.

### Durable guest-access implementation — Stage 8.5

Approved D004 is implemented in `src/server/guest-session.ts` and `guest-access.ts`: independent 256-bit bearer tokens with only SHA-256 verifiers stored; stable identity/seat binding; 30-day sliding expiry; revocation without membership deletion or ownership transfer; exact HTTPS-origin and host-only Secure/HttpOnly/SameSite=Lax cookie helpers. No account or recovery system is introduced. `003_guest_access.sql` is additive; existing private game frames and trusted lobby APIs remain unchanged.

Owner lobby/membership creation is atomic. Access serializes on credential then lobby rows; new admission also locks the current game head and validates its exact committed frame before treating it as finished. Existing members may reconnect during play/full capacity. New seats append clockwise after owner index 0, capped at eight; expired/revoked seats remain occupied. Assigned unfinished/pre-creation-rollback games keep admission closed. A later rollback never changes the old match roster to include newly admitted lobby members.

The match transition rechecks authenticated-lobby roster equality under its existing lobby lock, closing join-versus-prepared-start races without holding auth locks across a runtime queue. Legacy trusted lobbies have no automatic credential backfill/adoption. See `docs/guest-access.md` for APIs, lock order and residual integration boundaries. These libraries do not install HTTP/Socket.IO handlers, close expired/revoked sockets, infer game participation from membership, or make a returned binding a permanent authorization capability.

## Durable local host — Stage 8.7

`PostgresGameHost` in `src/server/game-host.ts` owns existing-game lease acquisition/restoration, current-lobby routing, aggregate seat presence, fault disposal/recovery and successful atomic successor adoption. Cold acquisition/lifecycle operations are serialized locally; no second writer or new persistence format is introduced. Each writer lifetime has a fresh epoch. Clock tasks are wrapped to detect swallowed runtime deadline failures; failed detach lookups evict stale connected views. Healthy shutdown checkpoints then disposes/closes every entry, including when another entry fails. See `game-host.md` for APIs, callback/non-reentrancy constraints, fault semantics and real PostgreSQL coverage.

The host accepts only trusted fresh guest bindings/canonical requests. It neither authorizes network operations nor implements publication delivery. Expired/revoked socket handling, authenticated evidence/selector resolution, transport epochs/sequences and bounded projected delivery remain future adapters.

## Authorized bounded live publication — Stage 8.10

The operator approved a server-private host lifecycle observer and bounded transport semantics. `PostgresGameHost.subscribe` forwards exact committed runtime notices and synchronously invalidates released epochs, then rebinds only successfully installed live replacements. Runtime/engine/persistence formats remain unchanged; listeners and reporters cannot hold authoritative queues through promises or failures. The transport never subscribes to private successor preparation.

`PenkyTransport` owns per-socket stream generations and bounded private capture plus wire queues. It authorizes each action/state through non-refreshing `inspectSeat`, checks current epoch/game/branch/roster/liveness, projects and starts actual emission in one synchronous observation prefix, and delivers exact actions before each final state. Initial/resync/recovery/successor baselines are state-only; invalidation discards unsent observations. Current-time and later-pause checks prevent delayed reveal disclosure. `AcknowledgedOutbound` permits one in-flight packet; an unpredictable nonce-backed Socket.IO receipt, timeout and count/byte bounds prevent unread recipients from growing underlying buffers. Network receipt waits occur outside host/runtime queues; uncertain emissions are never retried.

These are best-effort streams, not a reliable outbox. A fresh resync stream invalidates old work but cannot undo already-observed knowledge. The socket rate limiter now uses lifetime-stable identity, not rotating stream epochs. See `transport.md` for the externally observable receipt signature, initial bounds, resync/rebinding policy and verified real TLS/PostgreSQL cases. No UI or deferred incoming operation is introduced.

## Lobby agreement acceptance — Stage 8.18

D005 explicitly accepts the existing private per-socket routing instead of adding literal rooms. ## Atomic automatic consequences

`decide` expands a user command into one action batch containing its automatic consequences. Empty-handed pickup chains, penalty start, and penalty completion are recorded as events in that batch. The runtime must commit and broadcast the complete batch, never an intermediate state or an independent rollback point inside it.

Round completion and finalized exits are deterministic consequences of the completing card event. Stump-opening rights use the eligible round number internally, but repetition equality normalizes entitlement availability instead of hashing absolute round numbers.

Penalty choices reserve a donor's selected card until the procedure completes; then transfers are applied together. Normal play is suspended throughout, so cards cannot be spent concurrently. Responses use own-property lookups: a valid opaque seat identifier must not be confused with an inherited JavaScript property.

Private stump peek knowledge is stored separately from the card's physical location. Illegal peeking does not transfer the stump into the hand. Raw peek data and repetition keys remain server-only.

## Claims, evidence references, and withdrawal

- Claim records form an ordered ledger. The first unresolved record starts a vote; later accepted records wait without restarting the current timer. Penalties caused by a verdict finish before the next claim vote starts.
- Engine commands carry a canonical evidence reference and scope. These are **trusted internal inputs**: Stage 8.11 resolves chat/action IDs, authors, original scope, and active-branch provenance from server-owned history inside one runtime queue job. A browser must not be allowed to relabel an old message as a current episode.
- Spoken episodes use explicit stable keys; equivalent prose is not machine-deduplicated. Players settle disputed spoken identity socially, as specified.
- Automatic violations are immediately recorded as handled action incidents. Reporting one again does not create a second punishment. Reusing a resolved, tied, withdrawn, or still-pending claim's incident key is rejected.
- A claim vote includes active seats except the accused. Withdrawal consent includes active seats except the claimant, including the accused. The runtime blocks ordinary commands during absence and records timer suspension; the engine does not infer live socket presence.
- Withdrawal pauses an active ballot with its exact remaining milliseconds. A denial or timeout restores those ballots and that remaining duration; a queued claim whose vote has not started gets a fresh timer only when it actually starts.
- A deferred dealing verdict can still be withdrawn before its punishment starts. A request queued behind another procedure is honored before the matching deferred punishment; other punishments are not interrupted.
- During the last-card reveal, accepted claims freeze the reveal timer until the full claim queue is drained. Resumption is an explicit event; replay never obtains fresh time.
- Claim ledgers, automatic incident keys, and punishment-start markers are rollbackable state. The separately persisted lobby chat is retained across rollback, with its original author and branch/scope context; Stage 8.11 validates that provenance rather than trusting browser-supplied labels. Nested ancestor prefixes remain valid only up to every retained cutoff; abandoned messages cannot be relabeled.
