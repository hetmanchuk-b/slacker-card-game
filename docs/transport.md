## Hosting

Configure a PostgreSQL pool with connection/statement timeouts and a redacted error listener; run the existing migrations explicitly. Supply a `PostgresGuestAccess`, one `PostgresGameHost`, actual TLS key/certificate and exact canonical HTTPS origins:

```ts
const transport = new PenkyTransport({
  access,
  host,
  tls: { key, cert }, // Deployment-owned certificate material, never test fixtures.
  origins: ['https://penky.example'],
});
await transport.listen(443, '0.0.0.0');
// Shutdown order:
await transport.close();
await host.close();
await pool.end();
```

The listener is real HTTPS with TLS 1.2 minimum. No plain-HTTP mode, forwarded-header trust, TLS-terminating proxy mode, account system or credential recovery is added. Exact Origin checks apply to session endpoints, Engine.IO polling requests and WebSocket upgrades; CORS alone is not authorization. Session endpoints are intended for same-origin browser requests. `PenkyTransport` itself does not serve static assets or the Socket.IO client bundle. Stage 9.1's separate loopback development front door serves client assets and certificate-verifying HTTPS `/api/` proxying without changing transport trust; see `browser-client.md`.

`listen()` defaults to an ephemeral loopback listener and returns its HTTPS address. `close()` is idempotent: stop admission/watchers, invalidate peers, drain pending authentication/attachment and detach jobs, then finish listener shutdown. The caller owns and closes host/pool afterward. Configure DB timeouts: shutdown and revocation deliberately wait for admitted work to settle rather than abandoning its connection cleanup.

## Session endpoints

All endpoints require an allowlisted HTTPS Origin and **empty bodies**. They return empty responses, never token/session/seat/grant JSON. Responses use `Cache-Control: no-store` and `X-Content-Type-Options: nosniff`.

| Endpoint | Success |
| --- | --- |
| `POST /api/guest/session` | Commit a fresh hash-only credential, then set the approved Secure/HttpOnly/SameSite=Lax host cookie; 204 |
| `POST /api/guest/session/refresh` | Authenticate and slide durable expiry, then refresh the same cookie; 204 |
| `DELETE /api/guest/session` | Revoke the canonical cookie credential, invalidate its local sockets/pending work, drain detach cleanup and clear the cookie; 204 |

Issuance refuses an existing named guest cookie, even malformed, with 409 rather than silently replacing identity. Refresh without a valid credential returns 401. Delete accepts a canonical already-expired/revoked token to clear it but rejects malformed/ambiguous cookies. Other failures are fixed empty responses: 400 invalid body, 403 origin, 404 unknown route, 405 method, 429 rate limit, 503 unavailable. No exception/SQL/token diagnostics are returned. No state-changing GET exists. Browser cookie persistence/renewal requires these HTTPS responses; Socket.IO messages cannot emit Set-Cookie.

D004 is unchanged: 30-day sliding lifetime, revocation/expiry without seat release or owner transfer, no name/code recovery. Credentials are accepted only from `readGuestCookie`, not socket `auth`, URLs, request identity fields or stable session IDs.

## Lobby endpoints — Stage 8.15

Both routes require POST, an allowed HTTPS Origin and an existing canonical guest cookie. They accept only UTF-8 `application/json` (optional `charset=utf-8`), without compression. Raw bodies, including chunked bodies, are capped at 2048 bytes. No implicit credential issuance, discovery/code system, caller-selected identity or socket attachment is added.

| Endpoint | Exact body | Success |
| --- | --- | --- |
| `/api/lobbies` | `{ "requestId": "stable-creation-key" }` | 200 with original lobby/owner-seat identity |
| `/api/lobbies/join` | `{ "lobbyId": "opaque-lobby-id" }` | 200 with own durable membership identity |

Success JSON is exactly `{ lobbyId, seatId, position, isOwner }`. Position is the zero-based clockwise seat index, not a dealing/turn hint. No roster, current game, credential/session identity, expiry, raw membership binding or game state is returned. Successful final authentication precedes Set-Cookie refresh and synchronous response emission. Responses retain no-store/nosniff headers. Clients explicitly resync using the returned lobby ID; HTTP admission never attaches/rebinds a socket or grants old-match spectator access.

Creation request IDs are exact nonblank, well-formed strings of at most 128 UTF-16 code units; join lobby references use the existing 256-unit reference limit. Neither is trimmed/normalized; NUL, extra/identity fields and invalid shapes are rejected. JSON is parsed normally before exact-field validation. Creation identity is `(authenticated stable guest, requestId)`; retries across processes/restarts return the original lobby/owner seat before generating identities. A different guest using the same key creates its own lobby, not ownership access. There are no additional creation inputs to change under a key. Join uses existing `(lobby, guest)` membership idempotence and returns the same own seat/index, including running/full matches. These are identity results, not immutable game-state cursors.

The additive creation mapping, lobby and owner membership commit in one transaction under credential serialization. Failed transactions publish no identity or cookie refresh; retry the original creation key after a lost/failed response. Mappings are retained with membership, including after credential expiry/revocation; request keys are not credentials. New joins retain D004's locked capacity/current-game admission and locked-roster start checks. No access SQL locks are held while waiting for host/runtime queues.

Errors are fixed empty responses: 400 invalid media/encoding/body/shape, 401 missing/invalid/expired/revoked credential, 403 origin, 405 wrong method, 409 capacity or running-match admission, 429 rate limit and 503 unavailable/unknown lobby/storage failure. No rejected operation sets a cookie or exposes private diagnostics. Existing IP HTTP limits apply; create/join share an additional credential-hash bucket of 12 requests/minute, including retries/invalid bodies. Admitted commits drain on cancellation/shutdown; uncertain responses are resolved by retry, never by generating a new creation key.

Verified coverage: two pure contract tests, two added real PostgreSQL creation scenarios (cross-service/process recovery, atomic receipt failure) and nine real TLS/PostgreSQL scenarios covering exact allowlists/retries/restart, auth/shape/raw-byte/rate limits and 2/4/8 admission/capacity. Browser cookie behavior and readiness/house-rule UI remain unverified/deferred. Stage 8.16's separate suite below now verifies complete external matches.

## Lobby agreements and acceptance — Stage 8.18

D005 approves this server-only workflow and accepts existing private per-socket delivery in place of literal rooms. These routes require an existing cookie, exact HTTPS Origin, POST and strict UTF-8 JSON, like admission routes. They do not require a socket attachment and do not change the socket intent union. Raw bodies (including chunked input) are capped at 32768 bytes; stored text is at most 4096 UTF-8 bytes, empty allowed, verbatim with no normalization/NUL/malformed Unicode. Read/edit/acceptance requests share the existing HTTP/IP and 12/minute credential lobby bucket.

| Endpoint | Exact JSON body | Permission |
| --- | --- | --- |
| `/api/lobbies/state` | `{ lobbyId }` | Durable member |
| `/api/lobbies/agreements` | `{ lobbyId, expectedRevision, text }` | Immutable owner |
| `/api/lobbies/ready` | `{ lobbyId, expectedRevision, ready }` | Own durable seat only; strict boolean desired acceptance, not a toggle |

Success is 200 with exactly `{ lobbyId, revision, text, editable, members: [{ seatId, position, ready }], matchAgreements: null | { gameId, revision, text } }`. All nested fields are selected explicitly; no session/credential identifiers, private game state or card observations are included. Match agreements are the immutable text/epoch accepted at the current match's start; historical pre-migration/legacy games have null rather than fabricated bindings. Original match text remains readable after later lobby edits and rollback. Cookie refresh follows successful commit and final non-refreshing credential validation, with no-store/nosniff headers. This is request/response, not live lobby push.

`ready` means acceptance of the current agreements ONLY, not general match readiness. `revision` is a canonical nonnegative signed-bigint decimal string **acceptance epoch**, not a whole-view version or a reliable cursor. Initial owner-only lobbies start at epoch 0, unaccepted. Actual stored text changes, genuinely new durable members and successful member-backed match starts advance the epoch and clear every member's acceptance. Individual acceptance/withdrawal updates do not advance it, so different members can confirm the same epoch concurrently. Same-seat updates serialize with desired-state semantics. Reads may show different acceptance flags at the same epoch; clients must not cache/sequence the whole view by epoch alone.

CAS is checked before equality; stale expectedRevision returns 409 without mutation, even for currently identical text. A matching-epoch identical text submission while editable is a successful no-op retaining all flags. Membership retries, disconnect/reconnect, rollback, failed starts and accepted canonical start retries do not advance/reset consent. All durable members count, including owner/disconnected members; absence never grants consent or removes a seat. Readiness loss on credential loss follows D004's retained seats/no recovery policy, not implicit acceptance or owner transfer.

Both mutation routes are locked (409) while an assigned current game is not durably verified finished, including suspension or rollback before creation. Reads remain permitted. A rollback to a running match leaves later lobby text/consent untouched, locks mutations and exposes the original immutable match agreements separately. Stored state integrity failure is unavailable, never proof that editing is safe.

New member-backed starts recheck the locked roster and every acceptance at final SQL admission. They bind the exact final text/epoch without adding client agreement fields to the existing start intent, then atomically write agreement binding, clear flags and advance epoch with the old closure/new frame/lobby pointer/start receipt. Exact accepted retries resolve before this gate and never clear again. Zero-membership legacy trusted starts remain compatible. Late readiness/roster denials produce fixed start rejections (`not-ready` / `invalid-configuration`) while preserving the old writer and rollback window. SQL faults still fail closed; committed consent is not reset by a failed transaction.

Workflow HTTP errors are fixed empty responses: 400 invalid shape/Unicode/bounds, 401 credentials, 403 origin/nonmember/owner permission, 405 method, 409 stale epoch or locked workflow, 429 limits and 503 unavailable/storage/integrity failure. No error echoes text, private diagnostics or refreshes the cookie. Lost mutation responses can yield stale CAS on retry after an epoch change; read a fresh view rather than retargeting the old request. No mutation receipt ledger or general readiness flag is introduced.

## Socket contract

Namespace `/`, default `/socket.io/` path. Handshake `auth` must be empty; cookie authentication is checked before namespace admission. Both direct WebSocket and polling admission enforce Origin. A rejected upgrade may close the transport rather than return an application envelope.

- Incoming event: `client-message` with exactly one existing version-1 protocol object: `resync`, `submit-claim`, `owner-history`, `rollback`, `post-chat`, `chat-history`, `start-match`, or one of the ten gameplay intents below.
- Outgoing event: `server-message(message, receipt, acknowledge)`, carrying an existing `StateMessage`, `ActionMessage`, allowlisted `CommandAck`, owner-only `OwnerHistoryMessage`, public metadata-only `RollbackNoticeMessage`, redacted `ChatPage` or fixed `ErrorMessage`. The receiver must promptly call the Socket.IO acknowledgment callback with the **exact opaque receipt string**. This new transport receipt is not a gameplay command, cookie or reliable-delivery/replay capability.
- Deferred well-shaped intents return `unavailable`; malformed shapes use existing decoder errors. Technical failures never become gameplay punishments.

The first authorized resync attaches the socket to one lobby using fresh durable membership. Later resyncs must name that same lobby; switching lobbies requires a new connection. Multiple sockets per seat use the host's aggregate presence, not direct per-socket runtime disconnect commands. A member without a current match can attach but receives `unavailable` rather than an invented null-state/lobby DTO.

Membership is not spectator authorization. Each resync reauthenticates membership, checks the current durable match route and actual roster, and selects only the bound seat's live projection. A newly admitted member cannot inspect an older match after rollback, even rollback before creation. Ownership/finishing grant no additional card visibility. No generic lobby-room state broadcast, raw authoritative state/history/events or privilege elevation is introduced. Fresh seat-private action observations use the separate allowlisted action projector.

Final non-refreshing authentication happens before a fresh runtime observation. Projection and synchronous best-effort socket emission then have **no intervening await**, so slow authentication cannot replay an expired reveal. No network acknowledgment/delivery promise is awaited in a host/runtime queue. State/action delivery has a writer-plus-stream epoch and one per-socket increasing sequence allocator. Explicit resync, rollback and writer replacement establish a fresh stream; initial/recovery/resync baselines are state-only. Resync is not reliable action replay, an outbox or a command acknowledgment. Gameplay acknowledgments are separate and retain historical heads on duplicate delivery; they are not state-update cursors. Attached sockets now receive best-effort live updates automatically; explicit resync discards pending old observations and starts a new baseline. Wrong/current-game races fail conservatively and require a fresh request/connection, never silently retarget an old operation.

## Bounded gameplay routing — Stage 8.9

An authenticated resync must first establish the socket's one-lobby attachment. Gameplay intents contain game/branch but no lobby or actor authority. For every operation, the adapter resolves fresh membership, checks the current match route through the host, explicitly constructs a command with the authenticated seat and original request ID, and dispatches with the exact client branch and server-owned `human` controller.

Supported intents are `draw-card`, `play-card`, `take-bottom`, `open-stump`, `penalty-response`, `cast-vote`, `request-withdrawal`, `withdrawal-response`, `propose-bot`, and `replacement-vote`. Procedure/card/claim IDs, ballots, approvals and refusal nulls are preserved exactly; `absentSeatId` is only the replacement target. No browser intent is spread into a trusted command. Stage 8.11 adds `submit-claim` as described below. Stage 8.12 binds rollback and owner-history as separate administrative routes; Stage 8.13 binds post-chat/chat-history separately; Stage 8.14 binds start-match through separate canonical owner orchestration. Existing procedure replies now work with externally submitted claims as well as trusted fixtures.

The approved optional `dispatch.admit` guard runs inside the runtime queue before receipts/rules. It performs a non-refreshing credential check and verifies current socket liveness, expiry, actual roster membership and connected human control. Guard false is a headless `unauthorized`; guard infrastructure failure is a headless `unavailable`, not a runtime fault. Neither accepts/persists a command. An idle queued command cannot act through another tab's retained seat presence after its own socket was cancelled. Guards await only bounded server-owned authorization, never delivery or re-entrant queue work.

No turn, beat, stump entitlement or ordinary-play expected-version gate is introduced. Well-shaped current-branch attempts still reach the engine and can be accepted violations. Wrong-game routing returns fixed `wrong-game` without a head; an authorized stale branch/procedure returns the existing command rejection, never silent retargeting. Old accepted IDs cannot replay abandoned-branch actions. IDs retain the existing **per-runtime, not per-seat namespace**: same-ID/changed-payload or cross-seat collisions reject as `command-id-reused`; actor-bound identical retries execute once, including after durable recovery.

Only `makeCommandAck` output is emitted after dispatch commits and a final credential check succeeds. Acknowledgments contain outcome/head/duplicate or an allowlisted rejection, never cards, events, history, receipts or one-time observations. A duplicate's head is its historical committed head and must not regress a client's current state. An action admitted before disconnection drains atomically; canceled/expired/revoked peers receive no accepted acknowledgment, and the original ID settles later retry. Failed storage emits no accepted acknowledgment, faults/discards the draft through the existing host path, and later recovery uses durable state. Stage 8.10's independent publisher sends authorized state/actions; it never reconstructs observations from command receipts or acknowledgment retries.

## Authoritative claim submission — Stage 8.11

`submit-claim` uses the same authenticated attachment, membership/current-game routing, queued admission, controller checks, durable acknowledgments and final authentication as gameplay. Actor comes only from membership; evidence/accused/reason/request/branch references remain exact. The adapter calls `PostgresGameHost.submitClaim` and the approved `GameRuntime.dispatchClaim` seam, not an out-of-queue scope guess. No client scope/author or new DTO is accepted.

- Spoken evidence derives the current scope in queue order and preserves its explicit episode key. Descriptions are not semantically deduplicated.
- Chat lookup is scoped to the attached lobby. The immutable author seat must be the accused; original game/scope/head are retained. Ancestor chat is valid only within every fork's inherited prefix, including nested cutoffs. Retained abandoned-future messages cannot be relabeled as current evidence.
- Action evidence searches only the active inherited timeline. The initiating event, never later automatic consequences, identifies the actor. System/non-attributable/unknown actions are invalid. Replay establishes original pre-action scope; a successful first lead belongs to its newly started round, while a round-ending action still belongs to the closed round, not the next gap.

Unknown, wrong-author, wrong-lobby/game or abandoned references return ordinary `invalid-claim` acknowledgments without raw evidence/author/context diagnostics. Closed original scopes return `scope-closed`; automatic or already-claimed incidents retain `incident-already-handled`. These technical rejections never create punishment. Engine voting, withdrawal, deadlines, FIFO and false-claim rules are unchanged.

Fresh authentication precedes cached receipt lookup. Exact accepted retries return their original historical receipt before resolving mutable scope again, even after recovery; changed/cross-seat requests reject. Resolver/storage-read failure is sanitized `unavailable` without faulting gameplay or creating a receipt. Resolution and execution share one runtime queue job; no timer/play/rollback may overtake SQL resolution. Lookup operations require deployment DB timeouts. Chat creation still uses trusted server APIs; this increment does not expose chat/history/admin/start endpoints or claim complete online matches.

## Owner history and rollback — Stage 8.12

Both routes require an authenticated one-lobby attachment and fresh `requireOwner` membership. Current game ID is checked through the existing host; archived games after an actual successor start are not routed. Metadata access uses the immutable original owner from committed history, not `state.ownerId` or current active-player status. Finished/exited owners and rollback before creation retain history access; unrelated membership never grants it. Rollback mutation retains runtime connected-human/controller checks and a fresh non-refreshing admission guard before cached receipts. Final credential/liveness validation suppresses departed recipients without undoing admitted atomic work.

`owner-history` uses the bounded prepared wire slot. The host captures concrete history only inside `runtime.observe`, after checking runtime health, and projects only the established D003 metadata DTO. Final authorization, projection and emission share that queued observation; no await follows the final check. Same-head closure is captured as committed metadata. Receipt-time watch/generation fencing suppresses requests queued before resync as well as work invalidated during authentication or wire waits. History shares stream sequences and the 64 KiB prepared-frame ceiling; oversized histories fail closed. No pagination, raw archive endpoint or state preview is added.

`rollback` maps display branch ordinals/action versions from a fresh committed capture into the exact trusted runtime command. Dispatch happens after exiting observe (never reentrant); optimistic expected-head and closure checks reject intervening changes instead of retargeting. Retained source branches reconstruct accepted retries across forks/recovery, preserving request ID, actor, expected head, target and warning. A new archived/stale selector remains invalid. Do not pass the original branch as a dispatch branch gate: rollback receipts intentionally survive their source branch becoming archived. Unknown selectors return allowlisted unknown-target; owner/warning/head/closure/controller errors retain existing behavior. No new persistence/receipt/runtime API contract is introduced.

A successful committed rollback rotates the stream and emits approved `rollback-notice` metadata to each freshly authorized current participant, before its fresh action/state packets. The notice contains actor seat, ordinal target/expected head and ordinal result head only. This covers rollback before creation where no rebase action exists. No raw IDs, private observations or history are broadcast. Failed commits, duplicates, resync/recovery and successor baselines do not replay notices. Already observed human knowledge cannot be undone; bounded best-effort delivery does not guarantee offline receipt. See `protocol.md` for the additive version-1 envelope.

## Committed live/action publication — Stage 8.10

A resync-authenticated participant socket watches the lobby through the approved server-private `PostgresGameHost.subscribe` seam. It follows only successfully installed live writers; private successor preparation is never observable. Synchronous writer invalidation cancels old queued work before disposal, then committed replacements bind a new state-only baseline. The adapter makes one host acquisition attempt after invalidation; writer refusal/failure disconnects rather than forcing ownership or retrying unknown errors. A successfully recovered writer or successor rebinds existing authorized sockets automatically.

Each ordinary committed runtime publication delivers its **exact ordered fresh action pairs**, using `makeActionMessage`, then one captured final state using `makeStateMessage`. A job containing multiple actions preserves each adjacent action head, not a synthesized whole-job pair. Controls with unchanged action heads still publish state. Duplicate/rejected/checkpoint jobs add no observations when the committed view is unchanged. Creation/recovery/resync baselines never replay actions, receipts, peeks or inherited history. A baseline starts at its authorized emission point; observations already superseded while initial authentication waited are discarded, not replayed after that baseline.

Every action/state packet performs fresh non-refreshing credential/seat authorization and checks current game/roster, writer epoch, branch, stream generation, liveness and expiry. Projection and actual emission are synchronous within a fresh runtime observation, with **no intervening await**. Captured action pairs/final states are retained, but emission-time runtime time hides expired reveals; a later claim/disconnection that paused the same reveal also suppresses its face in an older queued state. Ordinary hand visibility is unaffected. Raw snapshots and pairs stay server-private.

Explicit resync invalidates old work when its validated request is received, before incoming queue/authentication delays. Rollback invalidates old-branch work synchronously on the committed notice; handoff, disposal, disconnect, revocation and shutdown invalidate old writer/socket work. Unsent observations are discarded. Already-emitted data cannot be recalled, and clients must reject stale epochs/branches and clear old interactions. No uncertain emission or private peek is retried. Delivery failure cannot fault/reapply an accepted game action.

All outgoing `server-message` packets, including command acknowledgments/errors, share a bounded wire queue. **Only one packet is in flight until its transport receipt arrives**. Its unpredictable per-emission nonce prevents speculative acknowledgments of predictable Socket.IO packet IDs from crediting unread frames. Timeout, invalid receipt, queue/byte overflow or projection/auth failure disconnects that recipient and requires reconnect/resync. A fixed final technical error may drain before closure after private work is invalidated. Other sockets and runtime deadlines continue; no network acknowledgment promise is awaited inside a host/runtime queue. Receipt means this emission was received, not that animations finished, nor exactly-once application consumption.

Default trusted `delivery` limits are 64 captured publications / 4 MiB serialized private capture, 32 queued/in-flight wire packets / 256 KiB accounted payload, a 64 KiB prepared-frame reservation, and a 2000 ms receipt timeout. Accounting includes a conservative framing/nonce allowance. Limits include active work, not just queued arrays; Socket.IO/Engine.IO buffering cannot grow with an unread recipient because the next emission waits outside authoritative queues. Oversized single frames fail closed. `delivery` configuration is server-owned; it is not accepted from clients. These are initial operational bounds, not new game punishments or a reliable outbox.

## Cancellation, expiry and revocation

A socket's AbortSignal is passed to the host's additive optional `attach(binding, signal)` seam. The host checks it **inside its serialized admission**, before connection insertion/presence. Cancelled queued attachments cannot briefly reconnect/unpause a revoked or departed seat. Already-admitted atomic commits are not undone: cleanup drains and detaches afterward. Disconnect/shutdown/revocation invalidate pending emissions immediately and dispose late detach handles.

`PostgresGuestAccess.inspect(token, nowMs)` is a server-private, non-refreshing durable check; it returns only the private session/expiry binding or null, with fixed storage failures. It does not extend `last_seen_at_ms` or expiry. `inspectSeat(token, lobbyId, nowMs)` additionally joins durable credential/membership/current-lobby data without refreshing expiry, returning only a server-private seat binding or null. It is used for automatic publication so an idle socket is not kept alive by other players' actions. Normal incoming authorized membership operations still apply the existing sliding policy. Clients should use the HTTPS refresh endpoint to renew their actual browser cookie.

The default non-refreshing scan cadence is 1000 ms (`authPollMs`, trusted test/operations option, 10–60000 ms). Idle sockets do not keep a credential alive. A refresh from another tab is observed durably, so stale expiry timers do not disconnect it. Storage failures fail closed. Server-mediated revocation invalidates all local active/pending peers after durable commit; external revocation/expiry is observed during a scan or an operation's credential check, not through immediate distributed notifications. Detection includes scan/query latency and depends on deployment DB timeouts. There is no distributed socket registry or account recovery.

## Technical bounds

These are transport limits, not gameplay punishments:

- Engine.IO packet limit 16 KiB before Socket.IO JSON decoding; binary headers/attachment streams are refused.
- HTTPS header size 16 KiB, maximum 40 parsed headers, 5-second header / 10-second request timeouts; session bodies accept no data.
- 60 connection attempts/minute/IP; at most 256 Engine.IO connections and 256 admitted/pending namespace peers.
- 60 session requests/minute/IP, with issuance additionally limited to 6/minute/IP.
- 20 application events/second/socket, 120/minute/credential, at most four queued operations/socket. The socket budget uses its immutable lifetime identity; rotating publication epochs/resync cannot reset it. Limits apply **before** event-name/argument validation; flooding malformed events cannot produce unlimited errors.
- Fixed-window limiter stores at most 4096 keys and refuses new keys at capacity rather than evicting active limits. Observed remote addresses are used directly, never forwarded addresses.
