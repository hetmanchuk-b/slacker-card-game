# Browser client — Stages 9.1–9.6

## Implemented boundary

React/React DOM with Vite supplies a small English-language, client-rendered shell: explicit guest session confirmation, canonical lobby creation, joining by known reference, own lobby/seat/owner identity restoration and explicit agreements/acceptance snapshots. Stage 9.4 adds explicit receipt-aware Socket.IO connection, owner first start and a projected game summary; 9.5 extends it with manual dealing, private own cards/closed stumps and D002 transient notices/reveals. Stage 9.6 adds own penalty contribution/refusal and private completed-transfer feedback. There are no ordinary-play, chat/claim/vote/history/rollback controls, bots or Three.js yet. The approved later increments are recorded in `IMPLEMENTATION_PLAN.md`.

The HTTP browser flows call only existing same-origin HTTPS POST endpoints: empty-body guest refresh/issuance, then `/api/lobbies` with the exact creation key or `/api/lobbies/join` with exactly `{ lobbyId }`. `LobbyCreation`, `LobbyMembershipClient` and `LobbyAgreementsClient` are the tested HTTP/storage/navigation seams; React handlers own user interaction rather than mount effects that could duplicate mutations. Creation coalesces concurrent submits, while explicit subsequent confirmation reuses the original key. Workflow requests reject overlapping intents instead of queueing or retargeting them.

Cookie credentials stay Secure/HttpOnly/SameSite=Lax in the browser cookie jar, never JavaScript storage or request identity fields. Creation `sessionStorage` stores **only** `{ version: 1, requestId }` under `penky.lobby-creation.v1`; 9.4's separate nonsecret first-start intent is described below. It contains no token, trusted seat, game state or observations. The key is saved after session authorization and before lobby dispatch, retained even after success so reload can explicitly confirm the original lobby. It is not a credential; cookie authentication still governs every request. Losing tab storage loses this retry locator; there is no discovery/recovery promise.

Fresh explicit creation refreshes first; only a 401 with **no saved lobby request** permits issuance. A named invalid cookie yields issuance conflict, not overwrite. A saved creation with missing/expired credentials never issues another guest to replay that reference under a new identity. Transport/network/timeout failures keep the key and expose fixed safe errors. Requests have a 15-second deadline, no automatic retry and no redirect following. Storage failure prevents an unrepeatable lobby dispatch. Unknown/extra membership response fields, invalid references and non-owner/nonzero creation identities are rejected, never displayed or logged raw.

## Join and restore — 9.2

Enter an exact opaque lobby reference; it is not trimmed or normalized. Joining and successful creation retain only `#lobby=<encoded reference>` in the current URL. This fragment is a nonsecret locator, not a credential or cached membership, and is not sent to the server on navigation. Opening the provided link in another tab shares that browser context's existing HttpOnly cookie. Locator parsing happens on page load; this is not a live hash router. Reload/open the link and explicitly select **Restore my seat**: no identity appears before a fresh authenticated join response, and no mutation runs automatically on mount.

The default join/restore refreshes the existing session and **never issues credentials**. First-time guests must explicitly check the new-guest consent box; only then may a missing session trigger issuance. Consent is cleared after each attempt and never persisted. A named invalid cookie still conflicts rather than being overwritten, and any saved creation reference prevents fresh issuance even with that consent. Explicit new identity creation is not recovery of a lost seat. A locator cannot prove the original guest: an already-valid different guest cookie may be admitted as a new member by the existing join API. Always keep/use the original browser session for restoration; no recovery, identity-substitution detector or guest-self endpoint is promised.

The locator is retained before join dispatch, so a lost committed reply can be resolved with the same target and credential after reload. Creation retry state remains separate and unchanged, even when joining another lobby; **Resume lobby creation** still confirms its original canonical lobby. Shared UI serialization prevents simultaneous create/join actions. Responses allow only the requested lobby, opaque seat, integer position 0–7 and consistent owner flag. No roster/current-game data or cached authority is stored. Unknown lobby/storage share generic unavailable feedback; full/running admission share generic conflict feedback. Existing members can rejoin full/running lobbies; no client-side capacity/game-state guess blocks them. No polling/automatic retry consumes the shared lobby request budget.

Native labeled required/max-length input preserves identifier case/spelling and validates on submission. Updating a locator clears prior custom validity as well as its accessible error state; a failed join cannot leave later creation/restoration browser-blocked. Controls keep visible focus and keyboard activation, with click-to-confirm/new-guest consent explicit.

## Agreements and acceptance — 9.3

After confirming membership, **Refresh agreements** explicitly reads `/api/lobbies/state`; there is no mount request, polling, live lobby push, autosave or credential issuance. Current saved text, acceptance epoch and ordered durable-seat acceptance are allowlisted snapshots. The epoch is only a CAS input: a refresh installs changed acceptance flags even when its epoch is unchanged. It is not a whole-view ordering cursor.

Only the confirmed owner gets an editor. Save uses `/api/lobbies/agreements` with exact `{ lobbyId, expectedRevision, text }`; accept/withdraw uses `/api/lobbies/ready` with exact `{ lobbyId, expectedRevision, ready }`, never an actor/seat/owner identity. Acceptance applies to **saved** terms, not an unsaved draft or general willingness to play. All durable members, including owner/disconnected members, remain required by the existing start gate. Actual edits/new members/successful starts reset all consent; identical saves, individual confirmations/withdrawals, failed starts and accepted start retries do not.

The editor permits empty text and checks well-formed Unicode/no NUL/4096 UTF-8 bytes on submit, not by treating character count as byte count. No trimming/formatting or HTML interpretation occurs. Native textarea input uses browser newline conventions; simply reading and saving existing CRLF terms without editing retains the original exact state string. Read-only text uses React text children/pre-wrap. Original match text and its accepted epoch have a separate read-only panel, never an alias/fallback to current lobby text; null legacy bindings are not fabricated. An unfinished current match disables both mutations, including acceptance, not just owner text editing.

Draft, last verified snapshot and error/refresh state are separate. Conflict/lock 409 is deliberately ambiguous; network, timeout or malformed success may follow a commit. There is no automatic mutation retry or retarget to a newly read epoch. Such failures disable mutations and keep only the old verified snapshot/local draft visibly stale and copyable; auth failures clear the workflow view and request membership restoration without issuing a new guest. Explicit refresh warns that it replaces any unsaved draft and clears old validity errors. Changing confirmed membership discards the entire old widget. Workflow requests share the App create/join in-flight guard, so another lobby operation cannot overlap a pending workflow request. No data or draft is persisted in browser storage.

## Receipt-aware connection and first start — 9.4

After authenticated membership confirmation, **Connect game** creates a fresh same-origin WSS Socket.IO client with handlers installed before `connect()`, `autoConnect:false`, `reconnection:false`, `forceNew:true` and volatile outbound commands. Cookie authentication stays browser-owned; no token, actor/owner, roster, clock or random outcome is supplied. Every `server-message(message, receipt, acknowledge)` echoes its exact opaque nonce promptly, including stale/ignored packets; receipts do not wait for rendering/animations. Only one uncorrelated connect/resync/start operation is pending, with a 15-second deadline. Disconnect/error/timeout drops the displayed baseline and fences old callbacks. Reconnect is explicit, never buffered offline command replay.

Resync uses a **new physical connection**, then sends the existing lobby resync intent. This intentionally avoids treating an old in-flight, uncorrelated state packet as the reply to a newer local resync. Delivery epochs are opaque; retired epochs (bounded to 64 per physical connection) and duplicate sequences are ignored, gaps/malformed used fields fail closed. Action/rollback ordering metadata is consumed but never becomes an authoritative state or observation cache. A new epoch's notice/action may precede its state. Same-head control states are installed; no monotonically increasing action-version filter rejects legitimate rollback/replacement. Only current validated state updates the displayed head, not command/start acknowledgment heads or historical identities.

An `unavailable` attaching response is **not proof of an unassigned lobby**. It permits an explicit owner proposal `start-match` with `expected:null`; the server alone checks actual routing, ownership, roster and consent. A verified assigned head with `state:null` remains an assigned match and disables a new first-start proposal. It does not become an empty lobby or authorize a new game. This increment deliberately does not implement successor starts.

Before first start dispatch, `sessionStorage` saves exactly `{version:1,requestId,expected:null}` under `penky.first-start.v1.<lobbyId>`. It is a nonsecret immutable proposal, not credentials, trusted membership or a current-head cache. Corrupt/unavailable storage blocks replacement of an uncertain original intent. Explicit **Retry original first start** reuses the exact request/intent across disconnection/reload, including known rejection or lost acknowledgment; there is no automatic retry/retarget. A matching successful/duplicate start acknowledgment triggers fenced reconnect/resync, never installation of its possibly historical game ID. Socket/HTTP controls share operation guards; idle stream updates do not release another widget's request lock. Missing/expired original credentials never cause socket-side guest issuance.

At the 9.4 baseline, the read-only summary retained only checked head, phase, public seat/card counts and suspension/connection metadata, discarding own cards, table faces, procedures, timed disclosures and fresh action observations. The 9.5 extension below adds bounded own-card/disclosure/draw-actor presentation, not replay of that discarded data. The decoder validates the used subset, not a pretend full decoder of every future projection field. Game/branch changes invalidate the prior agreements widget/draft without fetching or changing server consent; the UI warns to refresh agreements again. Same-route control updates/resync do not repeatedly erase drafts. No generic JSON view, history replay, permanent trump or dealing-turn hint is introduced.

## Manual dealing and transient disclosures — 9.5

**Draw card** clicks the face-down deck during an attached, running dealing phase. No next-recipient/turn inference disables attempts: accepted out-of-turn violations report the actual actor, keep no card and leave the initial notice unconsumed. Each deliberate click uses a fresh request ID with only the confirmed game/branch. Only one draw is pending, with no optimistic movement; matching accepted/rejected acknowledgments update feedback, never the baseline head. Disconnect/timeout is uncertain; reconnect and inspect before a new deliberate attempt. No draw retry, automatic replay or persisted draw reference is offered. Rotated/rollback streams invalidate obsolete pending draws and late acknowledgments.

`GameStream` now validates/detaches authorized own-hand faces and opaque own-stump handles, initial notice/reveal fields and relevant fresh draw observations. `DealingView` renders hand faces and closed backs without exposing handles or other seats' faces. The last actual draw actor/destination (or out-of-turn rejection) is separate from authoritative state, retained across the immediately following state only as current feedback, never reconstructed from count differences or replayed on state-only reconnect. Unused procedure/action observations remain discarded, not a private knowledge cache.

D002's initial notice may reissue only from a current server projection before the first successful draw. Public final-card presentation uses a monotonic removal deadline anchored when receiving the server's remaining duration. Same running timer updates can shorten but never extend it; duplicate positions/rerenders cannot restart it. Pause/procedure suspension hides the face, and a genuine resume uses the newly projected remainder. Expiry, disconnect, rollback, new epoch and unmount clear display/obsolete timer work. The recipient's ordinary private hand still includes their card. No permanent trump, public reveal history or next-recipient indicator is rendered. This is approximate local removal, not authoritative clock synchronization or a timer command.

Four new Chromium/HTTPS/PostgreSQL cases drive all 36 draws through independent 2/4/8-seat browser UIs, verifying two stump passes, private hand distribution, observable actors, initial notice resync/consumption and a deliberate violation. They check public reveal expiry independent of server callbacks, real disconnect/resume remainder, expired state-only reload and lost committed draw acknowledgment with no replay. WebSocket loss routing is registered before navigation. Browser clocks test local removal; the fixture wall controls guest expiry, while host gameplay deadlines use real time and are separately awaited. No trusted gameplay state/turn source chooses draws. These are dealing tests, not full browser matches or penalty/claim controls.

## Penalty contribution/refusal — 9.6

`PenaltyView` consumes only the current allowlisted penalty: public recipient/reason/eligible seats, its timer and the viewer's **own** response. A native labeled required select contains only own hand cards, and explicit submit reserves the chosen card; changing selection never submits. With fewer than two hand cards donation is unavailable, but an eligible seat can still explicitly refuse. Closed stumps are never donation options. No other responder selections or inferred response counts appear.

`GameConnection` captures the confirmed game/branch/procedure timer ID and selected own card (or null for refusal) in one existing `penalty-response` intent. One command is pending; acknowledgments update feedback, never hand movement, reservation state, transfer faces or current head. Only a server baseline confirms an own reservation/refusal, and cards stay in donors' hands until authoritative completion. Selection is in-memory and keyed by game/branch/procedure; state gaps, confirmed response, card removal/last-card status, pause/expiry, procedure/route/epoch changes, rollback, disconnect and resync clear obsolete drafts. Lost/ambiguous replies require explicit reconnect/inspection, with no response retry, offline replay or selection persistence. Other active procedures disable dealing rather than attempting to continue through them.

Penalty timers are anchored to monotonic receipt time. Updates of a running timer can only shorten its deadline; a paused timer freezes the server's remaining duration, and a resumed same-ID timer anchors a new deadline using that remainder. `RemainingTime` is a reusable display with non-live countdown text, avoiding repeated screen-reader countdown announcements. Zero is valid while awaiting the server. Reaching local zero disables response and clears an unsent selection, but sends no expiry/refusal and never fabricates completion or the interrupted turn.

Fresh `penalty-transfer` observations are strictly bounded, detached and accepted only when the viewer is the donor or recipient. Their separate current-action feedback survives the following baseline, then clears on the next action, route/epoch/rollback, assigned-null state, disconnect/uncertainty or explicit resync. No transfer journal/history/reconnect replay is added; recipients never learn reservations before completion. Existing hand visibility remains independent of feedback.

Nine new Node tests cover command/selection/ack/reset boundaries, zero/one-card refusal, own-only reservation validation, timer pause/resume/zero and fresh-transfer privacy. Three four-seat browser cases use actual UI dealing and penalties: reservation without movement/recipient disclosure, queued/all-refuse completion, reserved-card transfer after real timeout with pause/reconnect, and lost accepted ack with state-only reservation restoration/no retry. The later-penalty case explicitly uses an authenticated Node Socket.IO fixture to lead one round using the leader's own projected card and attempt an illegal own-stump click, then verifies exact round phase/turn restoration after UI refusals and real stale-procedure rejection. It does not claim play/open/peek UI implementation or use raw authoritative state. Shared `dealing-helpers.ts` waits for a real private initial notice instead of reading during a transient action/state gap. Browser clock advancement is kept below heartbeat deadlines; it proves local display behavior, while real host penalty expiry is separately awaited.

## Loopback HTTPS development

The source-only development launcher composes:

```text
browser -> loopback HTTPS front door + Vite assets
        -> certificate-verified loopback HTTPS/WSS PenkyTransport for /api/ and /socket.io/
        -> existing PostgresGuestAccess/PostgresGameHost
```

The upstream preserves the browser's exact Origin and cookie; it does not enable forwarded-header trust, rewrite authorization, terminate into HTTP, disable upstream certificate validation or change existing business routes. Vite filesystem serving is restricted to client sources/node_modules; server sources are denied and no server environment variables are exposed by the frontend configuration. This is **not** a production proxy/deployment mode. Both polling and WebSocket upgrades on `/socket.io/` preserve exact Origin/cookies and verify the upstream CA. Vite middleware mode is bound to the actual HTTPS front server for upgrades. Teardown drains transport/host work before destroying remaining front-door TCP/upgrade sockets. The development HMR socket remains separate from game transport.

Requirements: Node 24+, npm, a separately migrated development PostgreSQL database, and developer-owned local TLS key/certificate with a SAN for `127.0.0.1`. Supply a CA chain when needed; for self-signed local certificates the same certificate is the default upstream CA. Do not put TLS keys or database credentials in client source or public environment variables.

Example in a shell with these environment variables already set:

```sh
# DATABASE_URL points to your intended development database.
# PENKY_DEV_TLS_KEY / PENKY_DEV_TLS_CERT point to your private local TLS files.
# PENKY_DEV_TLS_CA is optional for the upstream CA chain.
# PENKY_DEV_PORT is optional, defaults to 5173.
npm run db:migrate  # explicit operator action, never automatic in npm run dev
npm run dev
```

The launcher prints `https://127.0.0.1:5173` (or the configured port), uses bounded pool connection/statement timeouts, logs fixed errors without SQL/credentials and drains frontend/transport/host/pool on shutdown. It never installs certificates or runs migrations itself. Public test fixtures are **not** development credentials for valuable data or production.

## Build, typing and linting

`npm run build` preserves server JS/declarations in `dist/` and additionally builds browser assets in `dist/client/`. Development sources and client sources are excluded from server emission. Vite is not a production asset-hosting policy. No new server API, schema or persistence format is introduced.

`tsconfig.client.json` checks JSX/DOM code separately. Shared protocol DTO type references currently traverse server source types, so Node ambient declarations are available for type checking only; imports into the runtime browser bundle remain type-only. Client lint rules prohibit runtime imports of Node/server/runtime/persistence/engine/projector/message-builder implementations. No Redux/query framework or React refresh plugin is required by this slice. Format/lint/type gates include TSX, CSS, HTML, root browser configs and browser tests, not merely existing Node TS files.
