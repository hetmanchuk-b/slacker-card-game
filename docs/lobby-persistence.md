# Lobby persistence and match handoff — Stage 7

## Approved seams

Stage 7 implements retained chat and actual next-match transitions at the existing persistence/runtime seams. `PostgresLobby` stores immutable lobby ownership, retained chat and the current game pointer. Tests cross `PostgresLobby`, `GameRuntime` and `PostgresSession` against real PostgreSQL. They cover retention, canonical context, idempotence, transactional handoff and rollback races, not browser authentication or UI readiness controls.

Owner/author session IDs are trusted stable guest identifiers, not cookie tokens. Stage 8.5 provides the separate `PostgresGuestAccess` credential/membership gate, described in `guest-access.md`. Future transport must use it to authenticate each operation and bind current-game seats; this storage interface is not a network payload or authenticated endpoint. No ownership transfer or additional gameplay rule is introduced.

`PostgresLobby.create(pool, binding)` idempotently binds a lobby to its owner session/seat; a conflicting owner is rejected. `PostgresLobby.open(pool, lobbyId)` recovers that stored binding without in-memory ownership metadata. These methods are private server operations, not authorization for a caller who merely knows the lobby ID. `postChat(input, nowMs, runtime?)` records original author, verbatim text and server-derived game/branch/scope context. Runtime-bound messages enter that runtime's queue before any database lookup, so a later card action cannot overtake their scope capture. Runtime time overrides the standalone pre-game timestamp argument. Whitespace is preserved; NUL/unpaired Unicode are technical input errors, not gameplay penalties. Pre-match messages require an empty current-game pointer. Retries preserve the original context even after rollback; changed payloads cannot reuse IDs. `messages(afterSequence?, limit?)` returns a stable ordered page; `message(messageId)` retrieves the original immutable record for a future authenticated evidence resolver. Chat is separate from rollbackable card history and survives forks and match changes.

`startMatch(request, inputs, current?)` accepts a server-approved next roster/configuration. `expectedGameId` and `expectedHead` pin the prior result; both are null for the first match. The head is checked again in the runtime queue and storage transaction, so an old result cannot authorize a start after rollback/refinish. It prepares a private initial runtime, then commits its frame, the prior game's rollback closure, the lobby pointer and the start receipt atomically. The old runtime's queue serializes this handoff against rollback. Preparation is not exposed or acknowledged before the transaction commits. `GameRuntime.handoff` does not run the ordinary old-game commit afterward. The successor takes the connection/writer lease; the retired runtime stops accepting mutations. Preparation failures leave the existing live match usable and do not close its writer. Failed handoff transactions fault/discard drafts, leaving the last durable old game recoverable and rollbackable. A successor INSERT failure rolls back the old frame/head too. A committed handoff seals the old window even after a process restart; start retries return the original game rather than preparing another one.

Lobby start receipts retain canonical request IDs/configuration. A caller must retry the same server-resolved request, not regenerate identities before looking up an existing intent through `startReceipt(commandId)`. That receipt contains private server card configuration: use it internally after authentication and never send it to a browser. Stage 8 will adapt browser intents to this internal interface. All subsequent traffic must route through the lobby's current live match; do not keep sending commands/connection notifications to the retired runtime. The transport must check both game ID and branch ID. Readiness/house-rule editing, bot strategy and bot policy across matches remain their existing later stages; this storage API receives a server-approved roster/context rather than inventing those policies. For lobbies created through authenticated guest access, the final transition rechecks the stored clockwise membership roster under the lobby lock and aborts stale preparation if a join won first. Empty membership preserves legacy trusted start behavior; it does not permit authenticated adoption of legacy lobbies. A failed handoff transaction still requires recovery from durable state. Stage 11a must add the agreed minigame-completion gate to the start transition before that feature ships.
